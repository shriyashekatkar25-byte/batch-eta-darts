I promise a finish time I can keep.

Mirrors: AI Functions Asynchronous API (Beta), Nov 9 2026

Up to 50,000 parse / extract / classify requests go in as one batch. The moment a user submits, the product has to say when it will be done. Which number should that be?

Board 1 · The decision

Which finish time goes on the submit screen?

Customer problem

An insurance ops lead drops 40,000 claim PDFs into a volume and calls the async API. She has a 9 a.m. review meeting. Today she gets "submitted" and nothing else, so she polls, guesses, and over-plans. A wrong finish time is worse than none: she will cancel the meeting or run it on half the data.

pin: problempersona: ops lead

Proposed change

Show one headline ETA the moment a batch is accepted, computed by simulating thousands of possible runs of this batch (size, function mix, chosen concurrency, current queue). The headline is a chosen percentile of those runs; a "likely by" P50 sits beside it in smaller type.

pin: changescope: submit + status page

Success metric

On-time rate ≥ 90%: share of batches that finish before the ETA we showed at submit time, measured weekly over all batches above 1,000 requests.

pin: north starwindow: weekly

Guardrails

  • Padding: shown ETA ÷ median actual ≤ 1.6 (no lazy over-promising)
  • Bad surprises: P(actual > 1.5 × ETA) ≤ 2%
  • Throttling: rate-limited retries ≤ 1% of requests
  • Cost: spend per 1k requests ≤ +5% vs. no-retry baseline
pin: guardrails4 thresholds

Stakeholders

  • AI Functions eng + serving capacity (queue model, concurrency caps)
  • Design / docs (how a percentile reads to a non-statistician)
  • Field + support (escalations when a promise is missed)
  • FinOps-minded admins (cost per 1k requests)
pin: peopleDRI: PM

What makes it hard

Document parsing has a heavy tail (a few 300-page scans), queues are busier on weekday mornings, and higher concurrency finishes sooner but triggers rate-limit retries that cost money. One honest number has to absorb all three.

pin: tensionspeed vs trust vs cost
Board 2 · Live simulation (seeded, simulated data)

The ETA dart board Paid in full?

The ETA comes from a forecast model at submit time; each dart is one simulated actual run of the same batch. A dart that lands left of the ETA line finished on time. The fraction that lands inside is our estimate of the on-time rate, and it tightens like 1/√n as darts pile up.

—Padding—ETA ÷ median, ≤ 1.6
—Bad surprise—P(>1.5×ETA), ≤ 2%
—Cost drift—vs no-retry, ≤ +5%

Board 4 · The math, from my Monte Carlo course

    
Throwing darts to price a promise

    

      

        
Fraction inside = probability

        
The oldest Monte Carlo trick: to find the area of a strange shape, throw random darts at a box around it and count how many land inside. Here the "shape" is the set of futures where a batch finishes before its ETA. Nobody can write that down in closed form (heavy-tailed documents, queue waits, retries), but we can simulate one future cheaply. So we simulate thousands.

        
p̂ = (# runs with T ≤ ETA) / n    count ~ Binomial(n, p)

        
The count of hits is Binomial, so p̂ is unbiased and its variance is p(1−p)/n. Four times the darts halves the error bar. That is why the band in the chart pinches as darts accumulate, and why "+500 darts" barely moves a 2,000-dart estimate.

        
SE = √(p̂(1−p̂)/n)    95% band ≈ p̂ ± 1.96·SE

      

      

        
Average height × width

        
Each run's finish time itself uses the second Ch1 idea: an expectation is a sample mean. Inside one run we draw 240 request durations, average them, and scale by batch size ÷ concurrency. That is "width × average height": the total work is the area under the per-request time curve.

        
T ≈ queue wait + (N / C) · mean(t₁…t₂₄₀) · capacity + straggler

        
Product example: cost per 1k requests is also an area, list price × (1 + retry rate) averaged over the mix, so the same simulation prices the cost guardrail for free. The Strong Law of Large Numbers is the promise underneath: with a fixed seed and enough darts, every estimate settles on the true value for this model.

SQL · did our promises hold?


-- illustrative table names
WITH b AS (
  SELECT batch_id, request_count, fn_mix_parse_share,
         concurrency, submitted_at, shown_eta_at, finished_at,
         timestampdiff(MINUTE, submitted_at, finished_at)  AS actual_min,
         timestampdiff(MINUTE, submitted_at, shown_eta_at) AS eta_min
  FROM   apm_lab.ai_batch.batch_runs
  WHERE  submitted_at >= current_date() - INTERVAL 28 DAYS
    AND  request_count >= 1000
)
SELECT date_trunc('WEEK', submitted_at)              AS wk,
       avg(CASE WHEN actual_min <= eta_min THEN 1 ELSE 0 END) AS on_time_rate,
       percentile(eta_min / actual_min, 0.5)          AS padding_ratio,
       avg(CASE WHEN actual_min > 1.5*eta_min THEN 1 ELSE 0 END) AS bad_surprise_rate
FROM b GROUP BY 1 ORDER BY 1;

      

      

        
Python · the ETA engine


import numpy as np
rng = np.random.default_rng(42)

def eta(n, parse_share, conc, durations, q=0.90, runs=4000):
    # durations: empirical per-request seconds by function,
    # sampled from apm_lab.ai_batch.request_log
    T = np.empty(runs)
    for r in range(runs):
        k = rng.random(240) < parse_share
        t = np.where(k, rng.choice(durations["parse"], 240),
                        rng.choice(durations["other"], 240))
        cap  = rng.uniform(0.9, 1.4)          # fleet load
        wait = rng.uniform(0, 12)             # queue minutes
        T[r] = wait + n / conc * t.mean() * cap / 60
    hit = (T <= np.quantile(T, q)).mean()
    se  = np.sqrt(hit * (1 - hit) / runs)
    return np.quantile(T, q), hit, se
